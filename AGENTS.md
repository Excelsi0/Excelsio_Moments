# AGENTS.md — постоянные инструкции для AI-агентов

Этот файл — обязательный контракт для любого AI-агента (и человека), работающего в репозитории **EXCELSIO 2.0**.
Правила действуют всегда, пока не изменены владельцем проекта через коммит в этот файл.

---

## 0. Контекст проекта (читать перед работой)

- Проект: **EXCELSIO 2.0**, персональный сайт-портфолио веб-разработчика и фотографа.
- Домен (план): `excelsio-moments.ru`.
- Репозиторий: `Excelsi0/Excelsio_Moments`, основная ветка `main`.
- Текущий этап: см. `docs/ROADMAP.md`. Незавершённые этапы не начинаются без разрешения владельца.
- Документация (`docs/`) — единственный источник истины по требованиям, архитектуре, дизайну и безопасности. Если код расходится с документацией — это дефект, а не «новая норма».
- Первая версия сайта живёт в `src/` (статический HTML/CSS/JS). Не удалять, не перемещать и не перезаписывать её файлы: это отдельный от 2.0 проект (D-021).
- Вторая версия разрабатывается в `apps/web/` (единственный npm-пакет, React Router Framework Mode).

## 1. Обязательные правила

1. **Перед каждым заданием изучай актуальную документацию проекта.** Минимум: `README.md`, `AGENTS.md`, `docs/REQUIREMENTS.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, а также профильный документ задачи (`DESIGN_SYSTEM.md`, `SECURITY.md`, `ROADMAP.md`, `TECH_STACK.md`).
2. **Работай только в пределах текущего репозитория.** Не создавай вложенных копий проекта, не пиши за пределами рабочей папки, не трогай чужие каталоги и системные файлы.
3. **Не изменяй архитектуру без объяснения причин.** Любое отклонение от `docs/ARCHITECTURE.md` требует записи в `docs/DECISIONS.md` (новый ADR) и явного упоминания в отчёте.
4. **Не устанавливай ненужные зависимости.** Перед добавлением пакета: (а) есть ли решение на стандартных средствах платформы, (б) чем обоснован выбор, (в) записан ли он в `docs/TECH_STACK.md`. Одна зависимость = один аргументированный коммит.
5. **Используй TypeScript со строгой типизацией.** `strict: true`, без `any` (кроме обоснованных границ с `unknown` + валидацией), без `@ts-ignore` без комментария-причины. Публичные данные валидируются Zod-схемами, а не приведениями типов.
6. **Создавай переиспользуемые компоненты.** Дублирование JSX/SCSS-блоков недопустимо: выноси в `app/components/ui` (презентационные) или `app/components/features` (доменные). Пропсы описываются типами, стили — через токены дизайн-системы.
7. **Соблюдай Mobile-first.** Базовые стили — для 360–400 px; далее `min-width` медиазапросы. Никаких `desktop-first` правок и горизонтального скролла на 360 px. Тестируй мысленно и инструментально именно узкий экран.
8. **Учитывай доступность и `prefers-reduced-motion`.** Семантическая разметка, фокус-стили, aria-атрибуты для иконочных кнопок и диалогов, тач-цели ≥ 44×44 px, контраст ≥ 4.5:1. Все анимации отключаются/упрощаются при `prefers-reduced-motion: reduce`.
9. **Не используй секреты непосредственно в исходном коде.** Пароли, токены, ключи, строки подключения — только в `.env` (вне git) или в GitHub Secrets. В коде — чтение через типизированный конфиг с валидацией на старте.
10. **Не выдавай непроверенные результаты за успешно выполненные.** Если команда не запускалась, тест не проходил, push не выполнен — так и пиши. Формулировки «должно работать», «вероятно» запрещены в отчётах о проверках; вместо них — что именно проверено и каким способом.
11. **После каждого завершённого этапа выполняй доступные проверки.** Минимум: типы, линтер, сборка. Если проверка невозможна в текущей среде (нет shell/Node) — перечисли, какие команды владельцу нужно запустить вручную, и не закрывай этап как «проверенный».
12. **Сохраняй законченные изменения в Git отдельными осмысленными коммитами.** Conventional Commits, один коммит = одна логическая единица, рабочее состояние после каждого коммита. Никаких `force push`, удаления веток, `rebase`/amend опубликованной истории, перезаписи чужих данных.
13. **Не переходи к следующему этапу без разрешения владельца.** Завершил этап → отчёт → ждать явного «продолжай».
14. **Отвечай пользователю на русском.** Код, имена файлов, типы, комментарии в коде и технические термины — на английском; объяснения, отчёты, документация — на русском.

## 2. Рабочий цикл (definition of done для любой задачи)

1. Прочитать документацию по теме задачи.
2. Составить короткий план (для задач из 3+ шагов — чек-лист).
3. Реализовать минимальным достаточным изменением, не расширяя скоуп.
4. Проверить: `npm run typecheck`, `npm run lint`, `npm run build` (+ тесты, если есть). Отметить, что реально запускалось.
5. Обновить документацию, если поведение/структура изменились (`docs/DECISIONS.md` — для архитектурных сдвигов).
6. Коммит с осмысленным сообщением.
7. Отчёт: что сделано, что проверено, что не проверено и почему, что дальше.

## 3. Соглашения репозитория

### Ветки и коммиты

- Основная ветка — `main`; она всегда в рабочем состоянии.
- Крупные этапы — короткоживущие ветки `stage/N-название` (например, `stage/2-scaffold`), слияние после проверки.
- Формат сообщений — Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`, `test:`, `perf:`, `build:`.
- Пример: `docs: add architecture and design system for excelsio 2.0`.
- В рабочей папке Acode GitHub-хранилище само создаёт коммит при каждом сохранении файла (сообщения генерируются автоматически). Это особенность среды, а не выбор агента: историю не переписывать, в отчёте указывать фактические хеши и честно отмечать расхождение с запрошенным сообщением коммита.

### Код

- Именование: компоненты `PascalCase.tsx`, хуки `useSomething.ts`, утилиты `camelCase.ts`, стили `Component.module.scss` или `component.scss` рядом с компонентом.
- SCSS: BEM-нейминг классов, токены дизайна только через CSS-переменные (`var(--ex-*)`), без «магических» цветов и отступов в компонентах.
- Типы и Zod-схемы домена — в `apps/web/app/lib/validation`, чтобы серверные `loader`/`action` и UI использовали один контракт.
- Данные страниц приходят через `loader`/`action` React Router. Никаких `fetch` к собственному серверу из компонентов и ручных клиентских кэшей.
- Серверный код — только в `app/server/*` или в файлах `*.server.ts`; он не должен попадать в клиентский бандл.
- Все тексты интерфейса — в одном месте (`apps/web/app/content/ru.ts`), без «случайных» строк в JSX.

### Безопасность

- Публичные API-эндпоинты не возвращают черновики, e-mail заявок и служебные поля.
- Загрузка файлов валидируется по MIME + размеру + перекодируется; EXIF вырезается.
- Любые новые внешние интеграции описываются в `docs/SECURITY.md` (что передаём, куда, зачем).

## 5. Ограничения среды разработки (Android / Acode)

- Проект ведётся в Acode на Android; рабочая папка — корень репозитория (`README.md`, `src/` и т.д. лежат прямо в ней).
- Встроенный терминал Acode — Alpine Linux (proot). Он не имеет доступа ко всем типам хранилищ устройства, поэтому Git-операции над папкой проекта могут быть недоступны из терминала; в таком случае используется Git-интеграция Acode/GitHub или команды владельца.
- Сессия AI-агента может не иметь инструмента выполнения shell-команд. Изменения файлов делаются инструментами агента; `npm`-команды локально выполнять не требуется.
- Проверки (`typecheck`, `lint`, `test`, `build`) выполняются в **GitHub Actions** (`apps/web`, Node 24). Утверждать «CI работает» можно только после фактического зелёного прогона workflow; до этого — писать «не проверено».
- Мобильная разработка = обязательное внимание к размеру бандла, количеству blur-слоёв и плавности на слабых устройствах.

## 6. Формат отчёта агента (обязательный)

1. **Среда** — где работали, какие инструменты доступны/недоступны.
2. **Сделано** — список изменений по файлам с краткой сутью.
3. **Проверки** — что запущено и с каким результатом; что не запускалось и почему.
4. **Git** — ветка, хеш коммита, статус push (или точная причина, почему не выполнен).
5. **Риски / отличия от документации** — с указанием ADR.
6. **Следующий шаг** — предложение, без самовольного продолжения.
