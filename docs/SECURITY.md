# SECURITY — EXCELSIO 2.0

**Статус:** предложение (Этап 1), обязательные требования для всех последующих этапов.
**Принцип:** сайт небольшой, но публичный и с админкой — значит, защищаемся от автоматических атак, а не от APT. Приоритет: не потерять контроль над админкой, не отдать чужие данные, не потерять контент.

**Связанные документы:** `ARCHITECTURE.md` (потоки, модель данных), `TECH_STACK.md`, `ROADMAP.md` (этапы 3–5, 8, 11).

## 2. Авторизация и сессии (Этап 4)

1. **Один тип пользователя:** `admin`. Роли не вводятся до появления реальной потребности.
2. **Пароль:** ≥ 16 символов, хранится как Argon2id (параметры по умолчанию `argon2` для продакшна: memory ≥ 64 MB, iterations ≥ 3, parallelism 1–4). Пароль нигде не логируется и не возвращается API.
3. **Сессия:** случайный 256-битный токен, в БД хранится только SHA-256 хеш; TTL 7 дней (абсолютный) + продление не чаще раза в сутки скользящим окном; при входе создаётся новая сессия (старые токены того же устройства не переиспользуются).
4. **Cookie:** `__Host-exs_session` (при возможности), `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, без `Domain`.
5. **Выход:** удаление/отзыв сессии в БД + сброс cookie. «Выйти на всех устройствах» — отзыв всех сессий пользователя.
6. **CSRF:** все мутации — только POST на свой origin. В каждом админ-`action` вызывается `requireAdmin`, который проверяет сессию и `Origin`/`Sec-Fetch-Site` (для не-форменных запросов — заголовок `X-CSRF-Token`), см. `app/server/security/csrf.ts`.
7. **Rate limit входа:** 5 попыток / 15 минут на `ip + login`; 20 / час на IP; задержка ответа 300–500 ms; при превышении — 429 и уведомление владельцу.
8. **Отсутствие user enumeration:** при неверном логине или пароле — одинаковый ответ и схожее время.
9. **Смена пароля** — инвалидирует все сессии, кроме текущей.
10. **TOTP (после релиза):** секрет шифруется ключом из env; при включении — резервные коды (хешированные).

## 3. Секреты и конфигурация

- Все значения — в `.env` (локально/на сервере) или GitHub Secrets (CI). В репозитории — только `.env.example` с именами переменных и комментариями без реальных значений.
- `.gitignore` обязательно исключает: `.env`, `.env.*` (кроме `.env.example`), `*.pem`, `*.key`, `*.p12`, `secrets/`, `*.sqlite`, `*.db`, дампы.
- **Проверка перед каждым коммитом:** `git diff --cached | grep -iE "secret|token|password|api[_-]?key"` — ручной просмотр найденного.
- Конфиг читается через Zod (`core/config`). Приложение **не стартует** при отсутствии критичных переменных — «тихий» дефолт для пароля/секрета запрещён.
- Ротация: `SESSION_SECRET`, токен Telegram-бота, SMTP-пароль — раз в 6–12 месяцев и немедленно при подозрении на утечку.
- Ключи хостинга/регистратора/домена хранятся в менеджере паролей владельца; в чат и в код не передаются (в т. ч. AI-агенту).

**Перечень переменных (черновик):**

```
NODE_ENV=production
PORT=3000
PUBLIC_SITE_URL=https://excelsio-moments.ru
DATABASE_URL=postgres://user:pass@host:5432/excelsio
SESSION_SECRET=<64+ random bytes, base64>
ADMIN_EMAIL=owner@example.com
ADMIN_PASSWORD_HASH=<argon2id hash>   # или создаётся одноразовым скриптом
STORAGE_DRIVER=local|s3
STORAGE_LOCAL_DIR=./.data/media
S3_ENDPOINT=… S3_BUCKET=… S3_KEY=… S3_SECRET=… S3_REGION=…
TELEGRAM_BOT_TOKEN=… TELEGRAM_CHAT_ID=…
SMTP_HOST=… SMTP_PORT=… SMTP_USER=… SMTP_PASS=… MAIL_FROM=…
```

## 4. Безопасность API

1. Все входные данные — через Zod-схемы; неизвестные поля отбрасываются (`.strict()` там, где важно).
2. Публичные DTO собираются явно (whitelist полей), черновики и служебные поля не попадают в ответ.
3. Единый формат ошибок без стектрейсов, путей и SQL.
4. Ограничения тела запроса: JSON ≤ 1 MB, multipart ≤ 15 MB/файл, ≤ 20 файлов, таймауты на запрос.
5. Rate limit по маршрутам: публичное чтение — щедрое (защита от парсинга при необходимости), форма — 3/10 мин на IP, вход — см. раздел 2.
6. `Cache-Control: no-store` для админских и приватных ответов.
7. Никаких CORS-«звёзд» для админских эндпоинтов; CORS вообще не требуется (один origin).
8. Health-эндпоинт не раскрывает версии и конфигурацию.

## 5. Безопасность загрузок (Этап 5)

1. **Whitelist форматов:** `image/jpeg`, `image/png`, `image/webp`, `image/avif`. Проверка по magic bytes, а не по расширению/`Content-Type` клиента.
2. **Безусловный ре-энкод** через `sharp`: любой принятый файл пересобирается, оригинал сохраняется в приватном хранилище (и никогда не отдаётся публично).
3. **EXIF/XMP/IPTC удаляются** (включая GPS-координаты). Дата/место съёмки вводятся вручную в админке.
4. **Лимиты:** 15 MB на файл, ≤ 40 МП пикселей (защита от decompression bomb), ≤ 12 000 px по стороне.
5. **Имена файлов:** `<sha256[:16]>.<ext>` в директориях по префиксу хеша; никаких пользовательских имён, путей, юникода.
6. **Запрещено:** SVG, GIF (анимация), TIFF, PDF, архивы, любые исполняемые файлы.
7. **Выдача:** только через контролируемый маршрут (`/media/<hash>/<width>.<fmt>`) с проверкой допустимых параметров; оригиналы — через авторизованный админ-маршрут.
8. **Удаление:** помечать на удаление и чистить фоновым скриптом; уже опубликованные страницы не должны ломаться (проверка ссылок перед очисткой).

## 6. Заголовки безопасности и CSP

Базовый набор (Caddy/Node):

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
X-Frame-Options: DENY
Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=()
Cross-Origin-Opener-Policy: same-origin
```

**Content-Security-Policy (целевой, production):**

```
default-src 'self';
script-src 'self' 'nonce-<per-response>';
style-src 'self' 'nonce-<per-response>';
img-src 'self' data: blob:;
font-src 'self';
connect-src 'self';
frame-src 'none';
frame-ancestors 'none';
form-action 'self';
base-uri 'self';
object-src 'none';
upgrade-insecure-requests
```

- Сначала внедряется в режиме `Content-Security-Policy-Report-Only` (Этап 10), затем — включение.
- Nonce выдаётся сервером при SSR-рендере и передаётся в инлайн-скрипт гидрации.
- Внешние домены (аналитика) добавляются точечно с обоснованием в этом документе; YouTube/Vimeo-эмбеды — только через `frame-src` для разрешённых доменов, либо через «постер + переход» (предпочтительно).

## 7. Приватность и обработка персональных данных

**Собираем (контактная форма):** имя, контакт (e-mail/Telegram), тема (опционально), сообщение, страница отправки, дата, хеш IP, user-agent.
**Не собираем:** паспортные данные, платёжную информацию, cookies третьих сторон без согласия, точную геолокацию.

Правила:

1. Уведомление о обработке ПД и ссылка на политику конфиденциальности рядом с чекбоксом отправки.
2. Заявки хранятся не дольше 12 месяцев, если не переросли в переписку; удаление — из админки.
3. IP хранится только как `sha256(ip + PEPPER)` — для лимитов и антиспама.
4. Аналитика — без персональных данных; при использовании Яндекс.Метрики — уведомление в политике; предпочтительно self-hosted Umami.
5. Экспорт данных по запросу субъекта (его же заявка) — вручную из админки; удаление — там же.
6. Самохостинг шрифтов и иконок — меньше сторонних запросов и утечек Referer.

## 8. Инфраструктура и эксплуатация (Этап 11)

1. **SSH:** только ключи, пароль отключён, `PermitRootLogin no`, отдельный пользователь деплоя, fail2ban/эквивалент.
2. **Firewall:** открыты 22 (или нестандартный), 80, 443. Файл БД (SQLite) и каталог `.data/` не находятся в публичном каталоге статики и не отдаются веб-сервером.
3. **TLS:** Let's Encrypt через Caddy, автопродление; HTTP → HTTPS.
4. **Docker / systemd:** контейнеры без `privileged`, приложение — от непривилегированного пользователя, данные (БД и медиа) — на отдельном томе/каталоге с ограниченными правами.
5. **Бэкапы:** ежедневно консистентная копия SQLite (`VACUUM INTO` или `.backup()`) + синхронизация медиа в отдельное хранилище; хранить 14 ежедневных + 4 недельных; восстановление проверяется и описывается в `docs/RUNBOOK.md`.
6. **Обновления:** пересборка образов при обновлении зависимостей; перезапуск с проверкой health; откат — предыдущий образ/тег.
7. **Мониторинг:** внешний uptime-check (1–5 мин), алерт в Telegram при падении; простой счётчик 5xx.
8. **Логи:** ротация, без секретов и ПД; доступ по SSH-ключу.

**Ответ на инцидент (кратко):**

1. Изолировать: отозвать все сессии админки, сменить пароль и `SESSION_SECRET`, при необходимости остановить сервис.
2. Оценить: что затронуто (БД, медиа, ключи), сохранить логи.
3. Восстановить из бэкапа, при утечке ключей — ротировать все (БД, Telegram, SMTP, хостинг).
4. Зафиксировать в `DECISIONS.md`/`RUNBOOK.md` причину и принятые меры; проверить, что дыра закрыта.

## 9. Чек-листы

### Перед каждым коммитом

- [ ] В диффе нет секретов, `.env`, дампов, ключей.
- [ ] Нет `console.log` с чувствительными данными.
- [ ] Новые зависимости обоснованы и записаны в `TECH_STACK.md`.
- [ ] Публичные ответы не содержат черновиков и служебных полей.

### Перед релизом

- [ ] `npm audit` — нет critical/high без плана устранения.
- [ ] Rate limits включены на входе и форме.
- [ ] Cookie-флаги и HTTPS проверены в production.
- [ ] CSP работает (сначала Report-Only, затем enforce) и не ломает гидрацию.
- [ ] Бэкап создан и восстановление проверено.
- [ ] Логи не содержат ПД и секретов (выборочная проверка).
- [ ] `robots.txt` закрывает `/admin` и `/api`; админка `noindex`.
- [ ] Health-check и внешний мониторинг настроены.
