# DECISIONS — журнал архитектурных решений (ADR) EXCELSIO 2.0

Формат каждого решения: **Контекст → Варианты → Решение → Последствия → Статус**.
Статусы: `предложено` · `утверждено` · `отклонено` · `заменено D-XXX`.

**Правило:** любое отклонение от `ARCHITECTURE.md`/`DESIGN_SYSTEM.md` оформляется новым ADR до внесения кода, а не после.

## D-001. Стратегия рендеринга: SSR вместо чистого SPA

**Статус:** предложено (требует утверждения владельца).

**Контекст.** Кейсы и фотографии распространяются ссылками в Telegram; нужны корректные превью (OG-теги) и индексация. При этом нужна простая поддержка одним человеком и один деплой.

**Варианты.**

1. SSR React через Vite SSR API в том же Fastify-процессе (гидратация).
2. Чистый SPA (CSR) + отдельные OG-эндпоинты/пререндер.
3. Next.js App Router fullstack.
4. Astro + React-острова.

**Решение (рекомендация).** Вариант 1: SSR для публичных маршрутов, CSR для `/admin`. Метаданные собираются на сервере из БД.

**Последствия.** Плюс: SEO и превью из коробки, свежий контент без пересборки, единый стек. Минус: нужно поддерживать `entry-client`/`entry-server`, учитывать SSR-ограничения (нет прямого доступа к `window`), серверная нагрузка выше CSR. Сложность считается приемлемой для одного разработчика.

**Альтернатива «на потом».** Если SSR окажется обузой, допустим переход на вариант 2 (SPA + пререндер статических страниц) с потерей per-page OG для кейсов — потребует нового ADR.

## D-002. Backend: Fastify + TypeScript (модульный монолит) вместо Next.js / BaaS / headless CMS

**Статус:** предложено.

**Контекст.** Нужны админка, авторизация, загрузка изображений, заявки. Требование проекта — Vite + React; сервисы-конструкторы (Headless CMS, Supabase) размывают контроль над SEO-метаданными и обработкой изображений.

**Варианты.** Fastify; Express; NestJS; Next.js API; Supabase/Firebase; Payload/Strapi/Directus; Django/Laravel.

**Решение (рекомендация).** Fastify 5 + собственные модули (`auth`, `projects`, `photos`, `media`, `applications`, `settings`) в одном процессе с SSR.

**Последствия.** Плюс: общий TypeScript-контракт с фронтендом, минимум слоёв, полный контроль над безопасностью загрузок и метаданными. Минус: часть «батареек» (админка, auth) пишем сами — зато без вендор-лока.

## D-003. База данных: PostgreSQL или SQLite

**Статус:** предложено, нужно решение владельца.

**Контекст.** Контент: проекты, блочный контент (`jsonb`), медиа-варианты, категории, заявки, сессии. Объём — сотни записей, трафик низкий. Бюджет — персональный проект.

**Варианты.**

1. **PostgreSQL 16+** (Docker на VPS): полноценные реляции, `jsonb`, FTS, надёжные бэкапы, привычный путь масштабирования. Стоимость: +1 контейнер, +память, бэкап `pg_dump`.
2. **SQLite** (файл на томе): нулевое администрирование, простой бэкап копированием, идеален для одного инстанса. Ограничения: конкурентная запись, миграция при масштабировании, меньше типов/индексов.
3. Управляемый PostgreSQL у провайдера: меньше операций, но дороже и внешняя зависимость.

**Решение (рекомендация).** PostgreSQL 16+ как основной вариант; Drizzle позволяет начать на SQLite и перейти на PostgreSQL без смены прикладного кода, если бюджет/операции окажутся критичны.

**Последствия.** Нужен Docker (или локальный PostgreSQL) и понимание бэкапов. При выборе SQLite — обязательный внешний бэкап файла и запрет на несколько инстансов приложения.

## D-004. Хранение медиа: локальный том или S3-совместимое хранилище

**Статус:** предложено.

**Контекст.** Фотогалерея: десятки-сотни фото × 6 размеров × 3 формата. Хостинг — один VPS. Бюджет ограничен.

**Варианты.** Локальный том; S3 (Yandex Object Storage / VK / Selectel); Cloudflare R2; хранение в БД.

**Решение (рекомендация).** Интерфейс `StorageAdapter`; старт на `local` (том + бэкап), переключение на S3 переменной окружения, когда объём медиа > ~2 ГБ или потребуется CDN/несколько инстансов.

**Последствия.** Код пишется сразу адаптер-совместимым (никаких прямых `fs`-вызовов в модулях домена). Бэкап медиа обязателен с первого дня. Cloudflare R2 отложен из-за вопросов оплаты из РФ (решение владельца).

## D-005. Авторизация: собственные серверные сессии (без внешнего identity-провайдера)

**Статус:** предложено.

**Контекст.** Один администратор, вход с телефона, максимальная простота и безопасность по умолчанию.

**Варианты.** (1) Собственные сессии в БД + Argon2id; (2) JWT в cookie; (3) Auth.js/NextAuth; (4) BaaS-авторизация.

**Решение (рекомендация).** Вариант 1. Token — случайные 256 бит, в БД — SHA-256 хеш; cookie `HttpOnly/Secure/SameSite=Lax`; TTL 7 дней; rate limit; CSRF-заголовок. TOTP — после релиза.

**Последствия.** Нет проблем с отзывом токена (в отличие от stateless JWT), нет внешней зависимости. Требуется аккуратная реализация CSRF и rate limit (этап 4) + тесты.

## D-006. Медиа-конвейер: `sharp` + blurhash на сервере

**Статус:** предложено.

**Контекст.** Нужны AVIF/WebP/JPEG варианты, вырезание EXIF, плейсхолдеры, стабильная работа на VPS без внешних сервисов.

**Варианты.** `sharp` локально; внешний image-CDN (Cloudinary/imgix/imgproxy); обработка на клиенте перед загрузкой.

**Решение (рекомендация).** `sharp` на сервере в очереди-обещании (без отдельного воркера): 6 ширин × AVIF/WebP/JPEG, blurhash. Клиентское сжатие — опционально как оптимизация трафика, но не как замена серверного ре-энкода (безопасность).

**Последствия.** CPU-пик при загрузке (приемлемо: загрузка редкая), требуется `libvips` в образе; генерация AVIF медленнее WebP — ограничить шириной ≤ 1920 для AVIF при необходимости.

## D-007. Админка: часть того же приложения, а не отдельный проект

**Статус:** предложено.

**Контекст.** Админка нужна одна, доступ только у владельца, мобильная.

**Варианты.** Отдельный SPA/поддомен; часть основного приложения с ленивым чанком и `noindex`.

**Решение (рекомендация).** Часть основного приложения: `/admin/*`, ленивый чанк, отдельный layout, `robots`-запрет, не грузится на публичных страницах.

**Последствия.** Один деплой, общие компоненты и типы. Риск: рост публичного бандла — контролируется разделением чанков и проверкой размера на каждом этапе.

## D-008. Хостинг: один VPS + Docker Compose + Caddy

**Статус:** предложено (требует решения владельца и данных о домене).

**Контекст.** Домен `.ru`, аудитория в РФ, бюджет 400–1200 ₽/мес, SSR требует Node-рантайма.

**Варианты.** (1) VPS (Timeweb Cloud / Beget / Selectel) + Docker Compose + Caddy; (2) Vercel/Netlify + внешняя БД; (3) shared-хостинг с PHP (не подходит под Node); (4) Kubernetes (избыточно).

**Решение (рекомендация).** Вариант 1. Авто-TLS, минимум операций, предсказуемая цена. Провайдер выбирается на Этапе 11.

**Последствия.** Нужны базовые навыки администрирования (SSH, Docker, бэкапы) — они описаны в будущем `docs/RUNBOOK.md`.

## D-009. Судьба первой версии сайта (`src/`)

**Статус:** требует утверждения владельца.

**Контекст.** В корне репозитория лежит рабочий v1 (статический сайт-фотопортфолио: `index.html`, `css/`, `js/`, `img/`, `icon/`). Для Vite-проекта каталог `src/` — стандартное место исходников приложения. Конфликт неизбежен.

**Варианты.**

1. Перенести `src/` → `legacy/v1/` отдельным коммитом на Этапе 2 (история Git сохраняет файлы; при необходимости развернуть v1 как архив/поддомен).
2. Оставить v1 в `src/` и назвать исходники приложения иначе (`app/`) — постоянная путаница.
3. Удалить v1 — **запрещено** без отдельного разрешения (`AGENTS.md`, раздел 4).

**Решение (рекомендация).** Вариант 1, но **только после подтверждения**: сначала коммит документации, затем отдельный коммит `chore: move v1 static site to legacy/v1`, затем scaffold.

**Последствия.** Контент v1 (фото, тексты, favicon) переиспользуется в новой галерее. Ссылки на старые URL проверяются на Этапе 10 (редиректы). Пока перенос не выполнен, файлы v1 не изменяются.

## D-010. Стилизация: SCSS + CSS-переменные + BEM (без Tailwind и CSS-in-JS)

**Статус:** предложено.

**Контекст.** Нужна уникальная дизайн-система с токенами (свечения, градиенты, анимации) и предсказуемая поддержка.

**Варианты.** SCSS+BEM+CSS-переменные; Tailwind; CSS Modules + SCSS; styled-components; Panda CSS.

**Решение (рекомендация).** SCSS-модули/партиалы с BEM-неймингом и дизайн-токенами в CSS-переменных `--ex-*`; один файл токенов как единственный источник значений.

**Последствия.** Токены доступны и в инлайн-стилях Motion-компонентов, и в CSS. Дисциплина BEM обязательна (проверяется на ревью). Тёмная тема единственная (см. D-012).

## D-011. Структура репозитория: npm workspaces (`apps/web`, `apps/api`, `packages/shared`)

**Статус:** предложено.

**Контекст.** Нужны общие Zod-схемы и типы между клиентом и сервером; SSR требует отдельной серверной сборки.

**Варианты.** (1) Один пакет: `src/` (фронт) + `server/` (бэк), общие типы в `src/shared`; (2) npm workspaces с `packages/shared`; (3) pnpm/turbo monorepo.

**Решение (рекомендация).** Вариант 2. Это не микросервисы: один деплой, один процесс. Пространство имён `@excelsio/shared` даёт явную границу и запрещает импорт серверного кода во фронтенд.

**Последствия.** Чуть больше конфигурации (3 `package.json`), зато контракт типов невозможно «случайно» нарушить. Если владельцу покажется сложным — допустим переход на вариант 1 новым ADR.

## D-012. Только тёмная тема

**Статус:** предложено.

**Контекст.** Концепция — кинематографичный почти чёрный фон со свечением. Светлая тема потребует второй палитры, второго набора свечений и проверки контрастов.

**Решение (рекомендация).** В 2.0 только тёмная тема; токены структурированы так, что добавление светлой возможно позже (`data-theme`).

**Последствия.** Экономия времени и предсказуемость дизайна. Пользователь не может выбрать тему — принимается как ограничение.

## D-013. Уведомления о заявках: Telegram (основной) + e-mail (резерв)

**Статус:** предложено.

**Контекст.** Нужно мгновенно узнавать о заявке; у автора уже есть Telegram; e-mail-провайдер может требовать настройки домена.

**Решение (рекомендация).** Telegram Bot API как основной канал, SMTP — резервный (и включённый лог в БД в любом случае). Ошибка отправки не мешает сохранению заявки.

**Последствия.** Токен бота — секрет; чат владельца должен быть явно задан (`TELEGRAM_CHAT_ID`). При блокировке Telegram у владельца остаются заявки в админке.

## D-014. SEO: серверные метаданные + sitemap из БД, без CMS-плагинов

**Статус:** предложено.

**Решение (рекомендация).** Метаданные страниц формируются сервером (title/description/canonical/OG/Twitter/JSON-LD); `sitemap.xml` и `robots.txt` генерируются приложением из опубликованного контента; 301-редиректы при смене slug — из таблицы `redirects`.

**Последствия.** SEO предсказуемо и тестируемо (`curl`-проверки в `ROADMAP.md`), но требует дисциплины: любая новая страница обязана иметь метаданные (проверка на ревью).

## D-015. Антиспам: honeypot + тайминг + rate limit, Turnstile — по необходимости

**Статус:** предложено.

**Контекст.** Персональный сайт: спам вероятен, но капча ухудшает конверсию и приватность.

**Решение (рекомендация).** Сначала базовые меры (honeypot, минимальное время заполнения 3 c, rate limit 3/10 мин, хеш IP). Cloudflare Turnstile — только если базовых мер окажется недостаточно (тогда — новый ADR + запись в `SECURITY.md`).

**Последствия.** Ноль сторонних скриптов на форме; при всплеске спама потребуется доработка.
