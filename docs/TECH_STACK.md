## 2. Почему React Router Framework Mode, а не Fastify + Vite SSR

| Критерий | Fastify + ручной Vite SSR (первая версия) | React Router 7 Framework Mode |
| --- | --- | --- |
| SSR | Собственные `entry-client`/`entry-server`, ручная передача данных | Встроено (`ssr: true`, гидратация, `HydrateFallback`) |
| Данные страниц | Отдельный REST API + клиентский слой + TanStack Query | `loader` на сервере, данные типизированы и приходят вместе с HTML |
| Мутации | REST-эндпоинты + ручная инвалидация кэша | `action` + автоматическая ревалидация |
| Формы без JS | Требовалась отдельная реализация | `<Form>` работает нативно (прогрессивное улучшение) |
| Cookie-сессии | `@fastify/cookie` + ручной код | Хелперы `react-router` (cookie/session API) |
| Загрузка файлов | `@fastify/multipart` | `request.formData()` / `parseFormData` |
| API/файлы | Плагины и контроллеры | Resource routes (route-модуль без компонента) |
| Кода-инфраструктуры | Заметно больше (сервер, роутинг, SSR-мост, клиент API) | Меньше: фреймворк закрывает общее |
| Порог входа для нового агента/разработчика | Нужно понимать связку из 3 частей | Одна документация и один способ делать вещи |
| Гибкость | Максимальная | Достаточная (middleware-хук, express-адаптер при необходимости) |

**Проверено по документации, что Framework Mode закрывает все нужные сценарии:**

| Требование | Механизм | Готово |
| --- | --- | --- |
| Публичные страницы с SSR и SEO | route-модули + `meta()` + `ssr: true` | да |
| Отдельные кейсы проектов | динамический маршрут `development.$slug` + `loader` + 404 | да |
| Фотогалерея | `loader` с фильтрами, `ImageGallery`, лайтбокс на клиенте | да |
| Авторизация администратора | `action` + cookie/session API + БД-сессии | да |
| Админка с CRUD | вложенные маршруты + `loader`/`action`, оптимистичный UI по желанию | да |
| Загрузка и обработка фото | `parseFormData` (multipart) + `sharp` в `action` | да |
| Контактная форма | `<Form method="post">` + Zod + антиспам | да |
| Telegram-уведомления | серверный модуль c `fetch` | да |
| Работа с БД | Drizzle в серверных модулях | да |
| Деплой на VPS | `react-router build` + `@react-router/serve`/адаптер за Caddy | да |
| Health/sitemap/robots/media | resource routes | да |

**Вывод:** собственная реализация Vite SSR + отдельный Fastify API **не нужна**. Отдельный API-слой остаётся полезным только при появлении второго потребителя (мобильное приложение) — в 2.0 его нет.

**Vite:** `@react-router/dev` 7.18.5 официально поддерживает Vite 7 и 8. Рекомендуется **Vite 7** (линия, на которой проверялись шаблоны RR7); Vite 8 допустим — окончательно фиксируется по результату `npm create react-router` на Этапе 2.

## 4. База данных: SQLite против PostgreSQL

### 4.1 Сравнение под задачу EXCELSIO (один администратор, сотни фото/проектов, низкий трафик)

| Критерий | SQLite (WAL) | PostgreSQL 16+ |
| --- | --- | --- |
| Стоимость | 0 ₽, файл на диске | +контейнер/сервис, RAM ≥ 256–512 MB |
| Администрирование | нет сервера, нет пользователей/паролей | нужен сервер, роли, `pg_dump`, обновления |
| Бэкап | файл/WAL + `VACUUM INTO`; атомарная копия | `pg_dump`/`basebackup` |
| Чтение | очень быстрое (локальный файл, без сети) | быстрое, но сетевая задержка |
| Одновременная запись | один писатель (WAL позволяет читать параллельно) | много писателей |
| Репликация/горизонтальное масштабирование | нет | есть |
| Возможности | `json` (текст), FTS5, нет `jsonb`/`timestamptz` | `jsonb`, `timestamptz`, полнотекстовый поиск |
| Риск при сбое питания | низкий при WAL + `synchronous=NORMAL` | низкий |
| Перенос на другой сервер | копирование файла | дамп/восстановление |
| Подходит ли EXCELSIO 2.0 | **да** | тоже да, но избыточно на старте |

### 4.2 Решение

**SQLite** как основная БД. Обоснование: один администратор, единичные записи в минуту, объём данных — мегабайты, весь трафик — чтение публичных страниц. PostgreSQL не даёт выгод, которые оправдали бы операционную сложность (контейнер, пароль, бэкапы, обновления).

Обязательные настройки при открытии соединения:

```
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
```

Дисциплина: короткие транзакции, никаких долгих операций (обработка изображений) внутри транзакций БД, `better-sqlite3` — синхронный API (быстро, но не блокировать event loop тяжёлыми циклами).

### 4.3 Миграция на PostgreSQL — не «переключение флага»

Если БД станет узким местом или понадобятся несколько инстансов, потребуется:

1. `drizzle-kit`: диалект `sqlite` → `postgresql`, новая конфигурация, **новый набор миграций** (SQLite-миграции не применимы: другой SQL-диалект и типы).
2. Драйвер: `better-sqlite3`/`node-sqlite` → `pg`/`postgres.js`; адаптер подключения переписывается.
3. Схема: `integer(timestamp_ms)` → `timestamptz`, `text({ mode: 'json' })` → `jsonb`, `integer(boolean)` → `boolean`, `text` с UUID — на `uuid` при желании.
4. Запросы: проверить всё, что зависит от регистронезависимости (`LIKE` в SQLite нечувствителен к регистру для ASCII, в PostgreSQL — нет), от `RETURNING`, от поведения `COLLATE`.
5. Данные: экспорт в CSV/JSON и импорт скриптом, сверка количества записей и связей.
6. Бэкап/деплой: `pg_dump` вместо файла, обновление `RUNBOOK`.

Оценка: отдельный этап на 1–2 сессии, с тестами на копии данных. Формулировка «Drizzle позволяет перейти без изменений кода» **неверна** и в проекте не используется.

## 5. Драйвер SQLite

| Драйвер | Плюсы | Минусы | Рекомендация |
| --- | --- | --- | --- |
| **`better-sqlite3` 13.1.1** | Зрелый, синхронный (простой код), встроенный `db.backup()`, совместим с Drizzle (`drizzle-orm/better-sqlite3`) | Native-модуль: нужна сборка/prebuilt под платформу (Node ≥ 22) | **По умолчанию** (VPS/CI: linux x64) |
| **`node:sqlite`** (встроен в Node) | Ноль зависимостей и сборки, работает в любом окружении, включая proot Android; Drizzle поддерживает (`drizzle-orm/node-sqlite`) | Статус RC в документации Node (26.x), API моложе, меньше примеров | Запасной вариант, если native-сборка мешает локальной разработке |
| `@libsql/client` | Файл локально + возможность Turso | Лишняя зависимость без нужды | Не сейчас |

Обе реализации подключаются через один файл `app/server/db/client.ts` — смена драйвера не затрагивает доменный код. Выбор между ними фиксируется тестом на Этапе 2 (сборка + `npm run build` в CI и, при желании, локально).

## 6. Медиа: экономный конвейер

- 3 ширины (480 / 960 / 1600) × 2 формата (AVIF, WebP) + OG-вариант 1200×630 = **7 файлов** вместо 18.
- `withoutEnlargement`, авто-ориентация, удаление EXIF/XMP, фиксированные `quality` для предсказуемого размера.
- blurhash для плейсхолдера (CLS = 0, «мягкое» появление).
- `Cache-Control: immutable` за счёт хеш-имён; в production раздаёт Caddy.
- S3-совместимое хранилище — через адаптер, включается переменной окружения (без переписывания кода).

## 7. Сборка и тесты при разработке с Android

Проблема: агент в Acode не имеет shell; терминал Acode — Alpine в proot и может не видеть папку проекта; `sharp`/`better-sqlite3` требуют native-сборки (на musl/arm64 это не гарантировано).

**Схема (рекомендуется):**

1. **Источник истины — GitHub Actions.** Каждый коммит в `main` и каждый PR запускают `npm ci`, `typecheck`, `lint`, `test`, `build` на `ubuntu-latest` с Node **24**.
2. **Агент** правит файлы и читает статус workflow (после Этапа 2 — через GitHub API/веб-интерфейс); локальные `npm`-команды не требуются.
3. **Локальный dev-сервер — опционально.** Если понадобится: терминал Acode, `apk add nodejs npm git`, `npm ci` в `apps/web`; при проблемах с native-модулями — переключение на `node:sqlite` (D-018) или работа только через CI + предпросмотр на VPS.
4. **Node-версия:** закрепить `.nvmrc`/`engines.node: ">=24"` и `node-version: 24` в CI; образ Docker — `node:24-alpine` (или `node:24-slim`, если musl-сборки `sharp` окажутся проблемными).

**Что нужно учесть:** файлы `.github/workflows/*` нельзя создать токеном без scope `workflow` — если плагин GitHub не сможет их закоммитить, файл добавляется вручную через веб-интерфейс GitHub (содержимое — в `ARCHITECTURE.md`, §13).

**Статус CI:** workflow ещё не создан и ни разу не запускался. Утверждение «CI работает» будет возможно только после фактического зелёного прогона.

## 10. Политика зависимостей

1. Каждый рантайм-пакет имеет в этом документе строку «зачем».
2. Сначала стандартные средства платформы, потом библиотека.
3. `package-lock.json` коммитится; обновления — отдельными коммитами.
4. Проверка размера бандла на каждом этапе; регресс > 20 KB gzip на публичном маршруте требует обоснования.
5. `npm audit` перед релизом; critical/high — устранение в течение 7 дней.

Dev: `@react-router/dev`, `vite`, `typescript`, `sass`, `eslint`, `prettier`, `vitest`, `@types/*`, `drizzle-kit`, `tsx`. Всё остальное — только через ADR.
